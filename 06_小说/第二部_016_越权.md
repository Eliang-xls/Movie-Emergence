二〇三六年。深圳。

老方的策元出了事。

老方不老--四十二岁,深圳人,硬件工程师。他加入超织体一年半,在三个策元里做过任务令。声誉分 1203,能证L1+。在超织体的网络里,他是一个中等偏上的节点。

他第一次和季深通电话的时候,季深问过他:"你怎么理解策元?"

老方说:"我以前在公司里,同事都是老板挑的。在这里--五个人,四个国家,我们从来没见过面。但我们都看中了同一个任务令。任务令上是这么写的--'环境传感器,农业场景,寻找有硬件、固件、数据、云端、测试经验的人。'

我点进去的时候,界面上弹出一个浮窗：一张网。五个节点,五种颜色。深圳是我。肯尼亚是昂戈。东京是佐藤。柏林是那个做数据的工程师。圣保罗是那个测试分析师。

连线的粗细表示互补性。我和昂戈之间的线最粗——固件和现场部署,互补性最高。我和佐藤之间的线是中等粗细——硬件和协议,有重叠。柏林和圣保罗的线最细——但他们和佐藤的线都很粗。

我盯着那张网看了十几秒。智契算过了——不是算我们的学历，是算我们每个人能做什么和需要什么之间的交叉点。一张网。五个从未见过面的人。然后状态变了：匹配完成。"

他停了一下。"我说不清楚。我只能说--它比招聘准。"

"就凭一条任务令?"

"一条任务令。加一个方向档案匹配。系统看我们每个人的方向档案--做过什么,做过多少次,做得怎么样。方向一致的人会被推到一起。你看这五个人--分别做硬件、固件、数据、接口、测试。系统先把我们各自的'方向'读了一遍,然后把方向互补的人放进了同一个房间。"

"像招聘?"

"不像。招聘是HR替老板选人。这里--没有人替谁选谁。是任务令自己--像一张网--把方向一致的人捞上来了。我说不清楚。我只能说--它比招聘准。"

他停了一下。

问题出在固件上。

但物流先卡住了。固件还没事。

老方的策元接的不只是"写固件"--是交付一千套真实传感器到肯尼亚农场。五个子任务令分别由五个国家的人领取。老方在深圳找传感器外壳供应商--华强北。外壳生产完成后需要发货到肯尼亚。

智能合约控制全流程。第六天晚上，合约状态从"进行中"跳成"待确认"。

状态跳成了"待确认"——合约在等一个它自己不能做的决定。这两个状态之间有区别。

老方打开合约日志。里面有三条记录：

"物流商 API 返回字段 `delivery_number = KN-2036-0471`。合约预设等待字段 `delivery_confirmation_code`。语义相似度：87%。字段结构相似度：94%。"

"自动建议：将 `delivery_number` 映射为 `delivery_confirmation_code` 的等效字段。风险：低（物流商该字段历史返回格式一致，过去6个月零变更）。"

"当前状态：待确认。合约设计规则：语义相似度超过 80% 时自动暂停执行，等待智权体签字确认映射关系。——该规则由策元聚结时的去中心化协议指定。"

老方看完了合约日志。合约认出了这两个字段是同一个东西——87%的语义相似度——但它没有自己做主。因为策元在成立时定下的第一条规则是："任何涉及物流链路误差的自动判定，需经过至少一个人类智权体签字确认。"

不是合约不够聪明。是当初设计它的人——佐藤——在 PCP 里写了一行限制："语义模糊度>10%时，不得自动决策。"

老方看着那行"待确认"。他点了一下"同意映射"。一秒后，合约状态变成"运行中"。

传感器到了肯尼亚。播种季还有两周。这时候他才发现固件的问题。

固件的问题，是老方的智契先发现的。

传感器在肯尼亚部署后的第四天，智契在任务令面板弹了一条异常报告。不是红色的——是琥珀色的。智契用颜色区分严重度：红是故障，蓝是信息，琥珀是"不确定"。

"温度传感器读数：实测值 vs 设计值，偏差0.31度。异常模式：只在环境温度超过37度时触发。信号强度：中。置信度：高。"

老方看了一眼。"0.3度。合规范围内。"

"设计标准是正负0.5度。当前读数在设计范围内。"

"那你为什么报？"

智契停了一秒。然后它做了一件老方没预料到的事——没有回答，而是把灌溉模型拉了出来，跑了一次模拟。

"如果温度持续偏高0.3度，水势模型会将土壤湿度误判为'低于临界值'——提前48小时触发灌溉。灌溉量：模拟显示每公顷多灌水1,200升。结果：种子在发芽期根茎腐烂。"

老方盯着那行字。

他知道智契不会自己写"根茎腐烂"这四个字——那是他从灌溉 Skill 里拉出来的作物模型。但它把两件事放在了一起：温度偏差 + 灌溉后果。它没有说"这很严重"。它只是把两张图拼在一起，让他自己看。

"播种季还有几天？"

"五天。"

"最坏情况？"

"三个农场的种子——全部淹死。一季口粮。"

老方坐在华强北的仓库里。那些传感器外壳在墙角堆着。他想起肯尼亚人在周报里写的那句话——"灌溉时机好像不太对"。那时候他没在意。现在他知道了。

智契又弹了一行字："修复方案：微调温度补偿系数。代码改动量：3行。测试周期：日本人建议的下一个版本需要两周。"

"两周赶不上播种季。"

"是的。两周赶不上播种季。"

智契在等他做决定。它把路标全插好了——偏差在，后果在，时间不够——但它自己不能修，只能等他选方向。

老方做了一件事--他没有等日本人修复,自己改了固件代码。他把修改后的固件提交到了策元的共享仓库里。没有经过日本人的同意。

日本人发现了。他在上面发了一条消息:"老方,你改了我的代码。你没有问我。"

老方说:"你的代码有bug。我修了。"

"你应该问我。这是我的模块。"

"五天后种子下地。农民等不到你的下一个版本。"

"如果你改错了呢?如果每个人都能改别人的代码,信任就碎了。碎了接不回来。"

"种子淹死了也接不回来。"

他没有等日本人回复就关掉了界面。他坐在仓库里，看着那批传感器。外壳做好了。固件修好了。但群里的那条消息还挂在那里——"老方，你改了我的代码。你没有问我。"

他知道这句话会一直挂在那里。那是他自己忘不掉的——跟日本人删不删无关。

---

这件事在超织体的网络里传开了。老方改了代码之后,策元的其他三个人分成了两派。

巴西人和肯尼亚人支持老方:"bug在那里,他修了,效率更高。"

德国人支持日本人:"模块边界是策元的基本规则。如果每个人都能改别人的代码,策元就乱了。"

争论从评论区蔓延到了策元的虚拟会议室。五个人开了三个小时的会。没有结论。

最后日本人退出了策元。

他在超织体上留了一段话:"我退出。老方改了我的代码,我不怪他。但他改了之后,策元没有机制处理这件事。没有仲裁。没有规则。只有投票--投票的结果取决于谁的声音大。"

他走了。

策元剩下的四个人在群里沉默了很久。没有人说话。最后巴西人打了一行字："他说的有道理。我们没有处理这种事的机制。"

肯尼亚人回了一句："但他走了。庄稼还在。"

老方没有回复群里。他一个人坐在华强北的仓库里，看着那批传感器。外壳做好了。固件修好了。但少了个人。他不知道为什么少了个人比修bug更难。

策元少了一个人。项目停了两周。老方找了一个新的固件工程师--一个印度人,声誉分比日本人低200。项目重新启动。但进度延迟了三个月。
