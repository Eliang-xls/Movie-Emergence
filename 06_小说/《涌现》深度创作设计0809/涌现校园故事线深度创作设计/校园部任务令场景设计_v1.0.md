## 一、林屿的第一个任务令——"创世涟漪"

**时间**: 2045年10月  
**场景**: 校园线章2-3  
**类型**: 创世任务令（CP_BOOTSTRAP）  
**目的**: 展示CONC冷启动机制+林屿的第一次"被验证"

### 任务令规格

```yaml
task_warrant:
  id: tw_campus_lin_001
  title: "修复一个你看不下去的东西"
  type: genesis_bootstrap
  dispatch: system_automatic
  trigger: "林屿完成能证声明后自动派发"

  objective:
    statement: |
      在CONC的文档、代码、设计中，找一个你觉得不对的地方。
      提交一个补丁 + 三句话说明。
      
      不需要完美。不需要全面。只需要一条——
      一条能让人说"嗯，这个人确实做过这件事"的记录。

  paths:
    path_b_micro_contribution:
      micro_tasks:
        - id: mt_001
          title: "修一个你看不下去的东西"
          deliverable: "一个可合并的补丁 + 三句话说明"
          verification: "AUTO（补丁可应用）+ PEER(3)"
          nr_reward: 100

  human_agent_workflow:
    lin_detailed:
      step_1_discover:
        human_role: "在校园CONC文档中找一个不对的地方"
        agent_role: "辅助搜索——扫描文档格式、链接有效性、术语一致性"
        pattern: |
          林屿在超织体的校园文档中浏览。
          他发现了一个问题：校园CONC操作手册中，关于"创世任务令"的说明
          有一处链接指向了一个已经不存在的页面。
          
          不是什么大问题。但他看到了。
          
          后颈——紧了一下。
      
      step_2_fix:
        human_role: "判断怎么修——是删掉链接还是更新为新地址"
        agent_role: "生成补丁代码——diff格式的修改"
        pattern: |
          林屿对Agent说："这个链接指向的页面已经不存在了。
          我查了一下，内容搬到了新的地址。帮我生成一个补丁。"
          
          Agent生成了diff。林屿看了一眼。改了两个地方：
          1. 链接地址更新
          2. 旁边加了一句说明："此内容已迁移至新地址"
          
          第二点是Agent没有加的——Agent只改了链接，没有加说明。
          林屿觉得：如果有人点了旧链接发现打不开，至少能看到一行字告诉他去哪找。
      
      step_3_submit:
        human_role: "提交补丁，写三句话说明"
        agent_role: "格式化提交——确保diff格式正确"
        pattern: |
          林屿写了三句话：
          
          "校园操作手册第12页的链接指向了一个404页面。
          内容已经迁移到了新地址。我更新了链接并加了一行说明。"
          
          他提交了。
          
          等PEER评审。

  peer_review:
    reviewers: 3
    dimensions:
      - name: completeness
        weight: 0.35
        question: "补丁是否完成了它声称要做的事？"
      - name: usefulness
        weight: 0.35
        question: "这个补丁对CONC网络有价值吗？"
      - name: process_quality
        weight: 0.30
        question: "提交过程是否规范？"
    passing_score: 3.0

  skill_output:
    L1: "修复校园CONC操作手册中的失效链接"
    L3:
      - decision: "在链接旁边加了一行说明"
        rationale: "只改链接不够——有人点了旧链接看到404，至少要知道去哪找。加一行说明比删掉链接更友好。"
    L8:
      philosophy: "能跑的代码不一定是好代码。能被别人读懂的才是。"
      aesthetic: "简洁。宁可多写三行注释，不省一行代码。"
      risk: "中。愿意尝试新方案，但先写回滚脚本。"
      style: "异步。写好文档，等人来读。不催。"

  rewards:
    nr: 100
    unlock: "自由创建/加入策元、领取自由任务令、参与PEER评审"
    vt: 12  # 第一批VT收入

  ghf_events:
    - type: task.claimed
      detail: "林屿领取创世任务令——修复失效链接"
    - type: task.completed
      detail: "林屿提交补丁。diff + 三句话说明。"
    - type: peer_review.completed
      detail: "PEER(3)评审完成。得分：3.8, 4.0, 3.5。通过。"
    - type: skill.generated
      detail: "Skill对象生成。L1-L8完整。L8四行字由林屿手写。"
```

### 叙事效果

- **后颈·涟漪**：林屿发现链接失效→后颈紧了→修复→涟漪来了
- **第一次被验证**：不是"他说他能做"——是"他做了，被人看到了"
- **VT收入**：12VT。不多。但是第一笔
- **L8的意义**：林屿填写的四行字——后来在方舟事件中被季深的L8对比，形成"真假印记"的张力

### 关键任务令详细设计

#### T1：传感器普查（林屿）

```yaml
task_warrant:
  id: tw_creek_T1
  title: "校园旧传感器普查——哪些还活着"
  assignee: ns_linyu
  day: 2-5
  estimated_hours: 12

  scope:
    - "走遍校园所有已知的传感器安装点"
    - "记录每个传感器的状态：完好/部分损坏/完全损坏"
    - "对部分损坏的传感器做初步诊断：什么坏了、能不能修"
    - "产出：传感器状态表（CSV格式）"

  human_agent_workflow:
    lin_detailed:
      day_2:
        - task: "走访东区食堂后面的传感器群"
          human_role: "物理检查——用手摸接口、用眼睛看锈蚀、用鼻子闻烧焦味"
          agent_role: "记录数据——林屿口述，Agent填表"
          pattern: |
            林屿蹲在东区食堂后面的管道井旁。
            传感器1号：外壳生锈，接口氧化。用砂纸打磨接口后灯亮了。
            传感器2号：线断了。两根线。需要重新接。
            传感器3号：完全损坏。外壳裂了，进水了。没救。
            
            林屿对Agent说："1号，接口氧化，打磨后可用。2号线断。3号报废。"
            Agent记录到表格中。
            
            这是典型的"人做判断+Agent做记录"模式——
            传感器的状态需要人去现场看、摸、闻。
            Agent不能替代——它没有手，没有鼻子。
      
      day_3_4:
        - task: "走访西区和北区"
          human_role: "物理检查"
          agent_role: "记录+统计——实时更新传感器状态表"
          pattern: |
            两天走了6个小时。脚疼。
            
            最终结果：
            - 总传感器：312个
            - 完好：89个（28.5%）
            - 部分损坏可修：127个（40.7%）
            - 完全损坏：96个（30.8%）
            
            林屿看着这个数字。312个传感器，只有89个还能用。
            但127个可以修——如果有人愿意花时间的话。
      
      day_5:
        - task: "整理普查报告"
          human_role: "审核数据——确认没有遗漏或错误"
          agent_role: "生成报告——状态分布图、维修优先级排序"
          pattern: |
            Agent生成了报告。林屿审核了两遍。
            
            第一遍：发现3个传感器的状态记录错了——
            林屿口述时说的是"部分损坏"，Agent记成了"完全损坏"。
            修了。
            
            第二遍：发现维修优先级排序有问题——
            Agent按"损坏程度"排序，但林屿觉得应该按"使用价值"排序。
            食堂旁边的传感器比图书馆后面的更重要——因为食堂用水量更大。
            
            林屿改了排序逻辑。"按日均用水量加权。"
            Agent不知道日均用水量——它没有这个数据。
            林屿从校园后勤的公开数据中找到了各区域的用水量。
            
            这个判断Agent做不了——它不知道"食堂比图书馆用水多"。

  verification:
    auto:
      - "传感器状态表存在，≥200条记录"
      - "每条记录包含：位置、状态、损坏描述、照片"
    peer: null

  skill_output:
    L1: "对校园312个旧水传感器进行物理普查，产出状态表和维修优先级"
    L3:
      - decision: "维修优先级按日均用水量加权，而非损坏程度"
        rationale: "损坏程度决定修的难度，但使用价值决定修的意义。先修高价值的。"
    L4: "旧传感器最常见的损坏是接口氧化（60%）和线路断裂（25%）。完全损坏的大多是进水导致的。"
    L8:
      philosophy: "旧设备不是废物。是被遗忘的资源。"
      aesthetic: "数据目录要干净。raw/ → repaired/ → connected/ 三级不能混。"
      risk: "宁可多跑一趟确认状态，不可修了才发现是坏的。"
      style: "我修设备的时候不看说明书。先拆开看结构。结构看懂了，修法自然就有了。"
```

#### T2：传感器修复（林屿）

```yaml
task_warrant:
  id: tw_creek_T2
  title: "修复可修的传感器——让旧设备重新呼吸"
  assignee: ns_linyu
  day: 5-20
  estimated_hours: 30  # 分散在两周内

  human_agent_workflow:
    lin_detailed:
      pattern: |
        林屿每天下午下课后去修传感器。2-3个。持续两周。

        1. 清洁接口——砂纸打磨、酒精擦拭
        2. 检查线路——万用表测通断
        3. 更换损坏部件——从报废传感器上拆零件
        4. 测试——接上电源，看灯亮不亮
        5. 记录——口述修复结果，Agent填表
        
        林屿的手越来越熟练。第一个传感器修了40分钟。第十个修了15分钟。
        第二十个修了10分钟。他的手记得住每一种接口的形状。
        
        Agent在每次修复后自动生成修复记录——时间、方法、结果、照片。
        林屿不需要手动写报告。
        
        这是典型的"人做物理操作+Agent做记录"模式。
        Agent不能替代林屿的手——它没有手。
        林屿不需要写报告——Agent帮他记。

  verification:
    auto:
      - "修复记录表存在，≥50条"
      - "每条记录包含：传感器ID、修复方法、修复结果、测试数据"

  skill_output:
    L1: "修复校园旧水传感器≥50个，成功率≥39%"
    L3:
      - decision: "从报废传感器上拆零件，而非购买新零件"
        rationale: "报废传感器的零件不是坏了——是整个系统坏了。零件本身还能用。零成本。"
    L4: "接口氧化是最常见的问题。砂纸打磨+酒精擦拭可以解决80%的氧化问题。"
    L5: "传感器修复检查清单（可复用）"
    L8:
      philosophy: "旧设备不是废物。是被遗忘的资源。"
      aesthetic: "修好的设备应该比新设备更可靠——因为你知道它哪里会坏。"
      risk: "宁可多测一次确认可用，不可装上去才发现还是坏的。"
      style: "我修设备的时候不看说明书。先拆开看结构。结构看懂了，修法自然就有了。"
```

### 与方舟的对比

| 维度 | "溪"策元 | 方舟策元 |
|------|---------|---------|
| 形成方式 | 自然聚结——方向一致的人找到彼此 | 韩霜邀请——表面"方向接近"，真实动机是接触深蓝 |
| 任务令 | 真实项目——修复旧传感器 | 安全治理——方向在被悄悄偏移 |
| VT来源 | 企业外包+校内项目 | 方舟内部VT流转 |
| 产出 | 可触摸的——50个修好的传感器 | 可触摸的——但方向已经偏了2.8度 |
| L8质量 | 有矛盾——"旧设备不是废物"vs"修了也可能再坏" | 太完美——"集体创作"的L8没有张力 |
| 结局 | 继续运转 | 冻结解体 |

### 关键任务令：方案选择（林屿的判断力考验）

```yaml
task_warrant:
  id: tw_brew_T_decision
  title: "Skill模板的技术方案选择"
  assignee: ns_linyu（策元委托林屿做判断）
  day: Day 45（策元成立后第45天）
  estimated_hours: 4
  type: phronesis_gate  # 决策门

  context: |
    Skill模板需要一个技术方案。Agent写了两个方案：
    
    方案A：更简洁，但扩展性差
    - 优点：实现快，3天能做完
    - 缺点：只支持当前的5种Skill类型，新增类型需要改代码
    
    方案B：更复杂，但扩展性好
    - 优点：支持任意Skill类型，新增类型只需配置
    - 缺点：实现慢，需要2周
    
    苏晴和陈默意见不一致。苏晴选A——快。陈默选B——好。
    他们把这个判断交给了林屿。

  human_agent_workflow:
    lin_detailed:
      pattern: |
        林屿坐在宿舍里。深蓝的灯环在安静地脉动。
        
        他看着两个方案的对比表。
        
        后颈——没有紧。涟漪——没有来。
        
        他在想一件事：酿造策元的方向是什么？
        
        "把经验变成可复用的东西。"
        
        可复用——需要扩展性。方案A更简洁，但简洁的东西不容易扩展。
        方案B更复杂，但复杂的东西更容易适应不同的场景。
```
