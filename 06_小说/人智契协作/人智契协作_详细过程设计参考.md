# 人+智契协作：详细过程设计参考

> 基于现实 AI Agent 突破性案例提炼的协作模式，转化为 CONC 世界中可小说化的详细过程。
> 目标：解决"人做了某个判断"叙事空洞的问题——展现判断是怎样在多环节拆解、迭代、反馈中一步步形成的。

---

## 一、从现实案例中提炼的五种核心协作模式

### 模式 A：四阶段收敛（来源：药物发现 HITL 流程）

```
Phase 1: AI 扩展可能性空间 → 生成海量候选方案
Phase 2: 人类战略性筛选 → 剔除"计算可行但现实无效"的候选
Phase 3: AI 深度模拟验证 → 在虚拟环境中压测幸存方案
Phase 4: 人类最终 Go/No-Go → 综合多维度判断
```

**关键洞察**：AI 的"错误"往往不是计算错误，而是**缺乏上下文**——组织特异性、系统效应、临床可行性。人类判断力补的正是这个缺口。

### 模式 B：驾驭工程（来源：OpenAI Harness Engineering）

```
人类做的事：
  - 定义"不变量"（必须遵守的架构边界）而非管理具体实现
  - 把隐性知识写进系统——"那次 Slack 上的讨论，Agent 感知不到就等于不存在"
  - 当 Agent 反复犯错时，不是让它"再努力一点"，而是问"缺了什么能力？"

Agent 做的事：
  - 生成全部代码、测试、文档、CI 配置
  - 自己审查自己、回复审查意见、修复构建失败
  - 连续运行 6 小时以上（通常在人类睡觉时）

关键洞察：人-Agent 协作的瓶颈不是 Agent 的能力，而是**人类判断力是否被正确地编码为 Agent 可执行的规则**。
```

### 模式 C：多智能体协同决策（来源：OriGene 虚拟生物学家）

```
Coordinator → Planning → Reasoning → Critic 四个 Agent 协同

Planning Agent 将复杂问题拆解为子任务 →
各专业 Agent 调用工具和数据库 →
Critic Agent 进行反思和试错 →
人类专家接收决策路径图，验证实验环节
```

**关键洞察**：拆解不是一次性的——Agent 在每一步都有"反思"机制（Critic），反思越多性能越好。但最终验证仍需要湿实验（物理世界反馈）。

### 模式 D：分布式多智能体制造优化（来源：振华重工 + 华为核心网运维）

```
多个 Agent 分别负责设计协同、采购管理、制造运营
实时调整数百个并行项目的生产计划
Agent 之间通过协议协商——不需要人类居中协调
人类负责设定策略优先级、异常情况的最终裁决
```

**关键洞察**：多 Agent 之间的协调不需要人类做"中间人"——协议自己跑。人类介入只在"协议无法解决的冲突"出现时。

### 模式 E：人领导 AI 团队学术范式（来源：arXiv 2512.11993 + Robin 科学发现）

```
Human Architect：设计功能、拆解模块、创建金标准测试集
Thinking Agents：帮助理解代码库、识别集成点、规划和审查（用推理模型）
Coding Agents：执行实际编码和测试（用快速模型）
四大策略：Decomposition → Planning → Testing → Review
```

**关键洞察**：不是"一个 Agent 一个任务"，而是**分层 Agent 团队**——思考层用昂贵推理模型，执行层用快速模型。人类在每个层级都有不同的介入方式。

## 二、模式如何映射到 CONC 世界

| 现实模式 | CONC 映射 | 关键概念 |
|---------|----------|---------|
| 四阶段收敛 | 智权体内部的任务令执行循环 | Sophia(生成) → Phronesis(筛选) → Sophia(验证) → Phronesis(决策) |
| 驾驭工程 | Agent 群的"能力架构"——人定义不变量，Agent 执行 | 人编码判断力；Agent 从"执行者"变为"被驾驭者" |
| 多智能体协同 | Agent 群内部子 Agent 分工（如 code-gen / code-review / doc 三个 Agent 协同） | 一个智权体的 Agent 群不是单体——是协作小组 |
| 分布式多智能体 | 策元内多个智权体的 Agent 通过协议层自动协调 | 策元核编排 API、事件总线、Gate 门控 |
| 人领导 AI 团队 | Human(Architect) + ThinkingAgents + CodingAgents 的分层结构 | 智权体内部：人定义策略 → 推理 Agent 拆解 → 执行 Agent 实现 |

## 三、场景一：单个智权体解决复杂任务——详细过程

### 3.1 场景设定

**任务**：某城市 CONC 基础设施管理的信任传播子系统出现间歇性异常——每隔 4-12 小时随机触发一次虚假安全警报，导致部分城区的水电网调度被自动暂停。已有三个策元尝试排查未果。

**承接者**：林屿（智权体 ns_linyu），系统架构方向，Agent 群配置为：
- `diagnose-agent`：异常检测与根因分析（推理模型）
- `sim-agent`：系统行为模拟（快速模型）
- `audit-agent`：GHF 审计链回溯
- `conc-runtime`：CONC 协议栈

**任务令状态**：已由策元核拆解为 DAG 子任务，当前节点为"根因定位与修复方案"。

### 3.2 详细过程（七个环节）

---

#### 环节 1：数据汇聚——Agent 做的第一件事

林屿没有打开任何日志文件。

她只是对 diagnose-agent 说了一句话："把过去 72 小时内所有相关的 GHF 事件、信任传播的 Gossip 消息、以及受影响城区的调度暂停记录全部拉出来。我不需要原始数据——给我异常模式。"

**Agent 做了什么**：
- 调用 GHF 审计链 API，拉取 72 小时内所有 `TRUST_ANOMALY_DETECTED`、`SCHEDULE_HALT`、`GOSSIP_RETRY` 事件
- 调用 Gossip 广播日志，提取信任传播的延迟分布和重试模式
- 调用受影响城区的调度日志，交叉比对每次暂停的时间戳
- 运行时序聚类算法，将异常分为三类：峰值型（集中在凌晨 3-5 点）、脉冲型（随机分布）、级联型（从单节点扩散到全网）

**产出**：一份三维异常聚类报告。diagnose-agent 说："三种异常可能指向不同根因。峰值型与市场结算周期高度相关（p=0.94）；脉冲型无明显时间规律；级联型每次起爆点都是同一个节点——ns_xu_water_east。"

**为什么这不是"降智为普通软件"**：Agent 做的不只是"检索数据"——它主动做了聚类、关联分析、显著性检验。相当于一个数据科学家在 30 秒内完成了需要人类团队三天的工作。林屿不需要知道这些算法——她只需要 Agent 的结论。

---

#### 环节 2：第一个判断点——排除噪音

林屿看着报告，沉默了几秒。

然后她说："峰值型先不管。市场结算周期的关联太强了——那大概率是经济层的正常波动被误标为安全异常。把精力集中在级联型上。"

**为什么这是"人的判断"而不是"按是/否"**：

Agent 给出了三种异常模式，每种都有统计显著性。但它不知道：
- 市场结算周期与信任传播的交互是**已知设计特性**——不是 bug
- 前三个策元失败的原因很可能就是在这个噪音上浪费了时间
- 级联型虽然发生率最低（仅 4 次），但每次都触发了真实的服务中断

林屿的判断基于她参与 CONC 早期协议设计的经验——她知道信任传播层的 Gossip 协议在结算高峰期会有正常的延迟波动。这个上下文不在 Agent 的训练数据里——或者说，Agent 知道这些数据但不知道"哪些重要、哪些可以忽略"。

**对应的现实模式**：药物发现 Phase 2——人类剔除"计算可行但生物学不可行"的候选。

---

#### 环节 3：假设生成——Agent 的深度推理

"好。聚焦 ns_xu_water_east。给它做全量回溯。"

**Agent 做了什么**：
- 对该节点的全部 GHF 事件（过去 90 天）做因果图构建——用 Granger 因果检验 + 贝叶斯网络
- 发现一个异常链：`NS_JOIN → SKILL_PUBLISH → TRUST_UPDATE → (72h gap) → ANOMALY_CASCADE`
- 每个级联事件的前 72 小时，该节点都恰好有一次 Skill 发布操作
- sim-agent 在隔离环境中复现：模拟该节点的 Skill 发布 → 观察信任传播的 Gossip 消息格式 → 发现 Skill 元数据的 `version` 字段在特定情况下被截断为 0 → 触发下游节点的 PEER 验证超时 → 信任分临时归零 → 触发安全协议 → 调度暂停

**sim-agent 的报告**："根因定位：Skill 发布的元数据序列化逻辑存在边界条件 bug。当 Skill 的 `version_history` 数组长度超过 127 时，8-bit 长度头溢出，version 字段归零。下游节点读到的 version=0 → PEER 验证判定为'未签名 Skill' → 信任分归零 → 安全协议触发。"

**为什么这是"智契的强大"**：Agent 在几分钟内完成了全量因果分析、隔离环境复现、精确定位到一行代码的边界条件。这是人类团队至少需要一周的工作量。

---

#### 环节 4：第二个判断点——不是"修 bug"，而是"评估影响面"

林屿看着 sim-agent 的复现结果，没有立即下令修复。

"这个 bug 只影响 ns_xu_water_east 吗？"

**Agent 的回应**："根据代码模式匹配，CONC 协议栈的 `serialize_skill_metadata()` 函数在所有运行 v2.4.1 版本的节点上都存在此边界条件。全网约 3,400 个节点使用该版本。但触发需要 Skill 的 `version_history` 超过 127 条——目前仅 ns_xu_water_east 满足此条件。"

林屿："还有哪些节点快到了？"

"按当前 Skill 更新频率，预计未来 30 天内会有 12 个节点触及 127 条阈值。60 天内会有 47 个。"

**为什么这是"人的判断"**：

Agent 找到了 bug，精确定位了代码，甚至预测了未来影响。但它无法回答的问题是：**修复的紧迫性是什么？修复方式的选择会对网络产生什么连锁反应？**

林屿的判断链条：
1. 这不是一个孤立 bug——它是协议栈的系统性问题
2. 如果只修 ns_xu_water_east，其他 47 个节点会在未来两个月内逐个爆炸——代价是被动响应 47 次
3. 但如果推送全局补丁，v2.4.1 是生产版本——3,400 个节点的协议栈同时热更新，风险巨大
4. 她需要在"被动修 47 次"和"主动更新 3,400 个节点"之间做权衡

她决定："联系策元核。我需要看 v2.4.1 节点的地理分布和所服务的城市基础设施类型。"

这个判断超出了 Agent 的计算范围——因为 Agent 不知道"什么风险是可接受的"。

---

#### 环节 5：方案生成与迭代——人与 Agent 的多轮对话

策元核返回了节点分布数据。v2.4.1 的 3,400 个节点中，有 210 个服务于关键基础设施（医院、电网、水网）。

林屿对 sim-agent 说："模拟三个方案。方案 A：仅修复 ns_xu_water_east。方案 B：批量热更新 210 个关键节点 + 其余节点渐进推送。方案 C：全局热更新。每个方案模拟 100 次——我要看最坏情况下的服务中断时长分布。"

**Agent 做了什么（第一轮）**：
- 在隔离模拟环境中并行执行 300 次模拟（3×100）
- 方案 A：100 次均无额外中断，但 47 个节点将在 60 天内逐一触发
- 方案 B：210 个关键节点的热更新中，最坏情况下 3 个节点出现 15 秒以内的 Gossip 断连
- 方案 C：3,400 个节点同时热更新，最坏情况下 27 个节点出现超过 2 分钟的 Gossip 断连，其中 4 个是医院节点

**林屿的第二轮判断**："方案 B 基本可行。但我们需要确保 210 个关键节点不是同时更新——按地理区域分 5 批，每批间隔 30 分钟。再跑一次。"

**Agent 做了什么（第二轮）**：
- 重新模拟分批方案
- 最坏情况改善到：每批最多 1 个节点短暂断连（< 5 秒）
- 无医院节点受到影响

**这不是"人在按是/否"——这是人在通过多轮迭代，用自己的风险认知逐步收紧 Agent 的搜索空间。**

---

#### 环节 6：第三个判断点——修复还是重新设计？

方案已就绪。但林屿停下了。

她让 audit-agent 回溯了一个更深层的问题："`version_history` 的 8-bit 长度头是为什么被设计成这样的？"

audit-agent 回溯了 GHF 中的设计决策记录，找到一份两年前的 ADR（架构决策记录，文档状态 D5 已归档）：

> "version_history 采用 8-bit 长度头以最小化 Gossip 消息体积。当时估计单个 Skill 的版本历史不会超过 20-30 条。127 条阈值被认为足够。"

林屿意识到问题的根源：两年前的假设已经过时。随着 CONC 网络的成熟，Skill 的迭代速度远超预期。不是修一个边界条件就够了——是整个 `version_history` 的数据结构需要重新设计。

她对策元核提交了一个**额外任务令**："`version_history` 从 8-bit 长度头迁移到 varint 编码。需要兼容 v2.4.1 节点（渐进迁移）。"

**为什么这是"人"的贡献而非 Agent 的**：Agent 找到了 bug 的代码位置和修复方案，但它不会主动质疑"为什么这个设计一开始就存在"——那是建筑师级别的判断。林屿把一次"补丁修复"上升为一次"架构改进"。

**对应的现实模式**：Harness Engineering 中的"垃圾回收"和"金科玉律"——不只是修 bug，而是把 bug 背后的设计缺陷编码为系统的不变量。

---

#### 环节 7：部署与观察——闭环

分批热更新按计划执行。林屿没有坐在屏幕前盯着进度条。

她让 monitor-agent 设置了一个观察窗口：24 小时内，所有受影响节点的 Gossip 延迟、PEER 验证通过率、误报次数。如果任何指标偏离基线超过 2σ，自动暂停剩余批次并通知她。

然后她去睡觉了。

凌晨 4 点，她的 Agent 发来一条消息："第三批（电网节点）中 ns_power_south 的热更新后 Gossip 延迟短暂飙升至基线 3.2σ。已自动暂停第四、五批。等待您的判断。"

林屿看了一眼——ns_power_south 的延迟在 3 分钟后恢复正常。这是电网节点独特的网络拓扑导致的，不是补丁的问题。她说："继续。"然后翻身继续睡。

**为什么这是"人+智契"的倍增**：Agent 在人类睡觉时完成了 300 次模拟、自动执行部署、实时监控异常、自主暂停。但暂停后的判断——"这是真异常还是假阳性"——仍然是人做的。两者的配合不是在同一个时间切面上——而是 Agent 承担了 99% 的时间窗口，人只在关键时刻介入。

---

### 3.3 总结：七个环节中的判断力分布

| 环节 | Agent 做了什么 | 人做了什么 | 判断力的性质 |
|------|---------------|-----------|-------------|
| 1. 数据汇聚 | 全量数据拉取、聚类、关联分析 | 下达指令 | — |
| 2. 排除噪音 | — | 识别"已知设计特性 vs 真实异常" | 经验+上下文 |
| 3. 假设生成 | 因果分析、隔离复现、精确定位 | 指定聚焦方向 | — |
| 4. 影响面评估 | 代码模式匹配、未来预测 | "修一个还是修全部"的风险权衡 | 风险容忍度 |
| 5. 方案迭代 | 300 次并行模拟 | 收紧约束条件（分批/间隔） | 渐进收紧搜索空间 |
| 6. 架构判断 | — | 发现两年前的设计假设已过时 | 系统性思维 |
| 7. 部署闭环 | 自动部署、实时监控、异常暂停 | 判断暂停原因是否为假阳性 | 关键时刻的最终裁决 |

**关键叙事点**：林屿的判断不是在真空中做的——每一步判断都建立在上一步 Agent 产出的信息基础上。Agent 缩小了不确定性空间，然后人做出方向选择；方向的后果又被 Agent 模拟验证，人再根据验证结果进一步收紧。这不是"人按一下按钮"——这是一个**收敛循环**。

## 四、场景二：策元内多智权体协作——详细过程

### 4.1 场景设定

**策元**：`gu_coastal_resilience`（滨海韧性），由 7 个智权体在"提升沿海城市气候适应能力"的创意图元下自发聚合。

**成员构成**：
- **何也**（ns_heye）：水文工程师，Agent 群含 hydrological-model-agent、flood-sim-agent
- **陈屿**（ns_chenyu）：交通系统架构师，Agent 群含 evacuation-opt-agent、traffic-sim-agent
- **苏敏**（ns_sumin）：通信基础设施专家，Agent 群含 network-resilience-agent、signal-propagation-agent
- **方旭**（ns_fangxu）：医疗资源规划师，Agent 群含 resource-allocation-agent、casualty-estimation-agent
- **季深**（ns_jishen）：公共信任与行为建模方向
- **策元核**（轮值中，当前 ns_heye）：负责任务令 DAG 拆解与编排
- **周敏**（ns_zhoumin）：社区联络，负责需求采集与方案落地沟通

**项目**：为滨海市设计 CONC 集成的台风应急响应系统。

**项目规模**：策元核将项目拆解为 23 个任务令，分布在 6 条并行工作流中。设计周期约 14 天。

### 4.2 协作过程（六个阶段）

---

#### 阶段 1：策元核拆解——从"一个项目"到"一张 DAG"

策元核（何也的 Agent 群中的 orchestration-agent）将"设计台风应急响应系统"拆解为 DAG：

```
                    ┌─────────────────┐
                    │ G0: 需求定义     │
                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
     ┌────────────┐  ┌────────────┐  ┌────────────┐
     │ 水文建模    │  │ 交通疏散    │  │ 通信韧性    │
     │ (何也)     │  │ (陈屿)     │  │ (苏敏)     │
     └─────┬──────┘  └─────┬──────┘  └─────┬──────┘
           │               │               │
           └───────┬───────┴───────┬───────┘
                   │               │
                   ▼               ▼
          ┌────────────┐   ┌────────────┐
          │ 医疗资源    │   │ 公共信任    │
          │ (方旭)     │   │ (季深)     │
          └─────┬──────┘   └─────┬──────┘
                │                │
                └────────┬───────┘
                         │
                         ▼
                  ┌────────────┐
                  │ 集成测试    │
                  │ (全员)     │
                  └────────────┘
```

**协作协议在做什么**：
- G0 Gate 定义了统一的需求规范——所有子任务以此为"已完成"的判断标准
- 每个任务令被分配后，工作区自动创建对应的 `docs/specs/` 子目录
- GHF 开始记录所有事件
- 并行工作流之间的依赖关系被编码为 Gate 的前置条件（如：交通疏散模拟需要水文建模的洪水淹没区数据 → `G1_evacuation.requires = G1_hydrology`）

---

#### 阶段 2：并行探索——每个智权体独立推进

**何也的水文建模流**：

hydrological-model-agent 拉取了滨海市过去 50 年的台风路径、潮汐数据、地形高程图，生成了一套风暴潮淹没模型。但这个模型有一个关键不确定性：滨海市过去 5 年大规模填海造地，地形高程数据已经过时。

何也的判断："用地形高程的卫星遥感数据交叉验证。如果填海区域的高程偏差超过 0.5 米，标记为'高不确定性区域'——后续交通疏散规划必须考虑这个冗余。"

hydrological-model-agent 调用卫星遥感 API，发现 23% 的沿海区域高程偏差超过 0.5 米。模型自动增补了 ±0.5 米的水位容忍区间。

**陈屿的交通疏散流**：

evacuation-opt-agent 基于何也共享的洪水淹没区数据（通过策元事件总线自动同步），开始计算最优疏散路线。它跑了 50 万次蒙特卡洛模拟，输出了三条推荐路线。

但陈屿看了一个细节后推翻了两条："路线 B 和路线 C 都经过了中山路——那是老城区的高架桥，台风天桥面风速超过 40m/s 就会封闭。你的模拟没有考虑桥梁的抗风等级。"

**为什么这是"人的判断"**：evacuation-opt-agent 知道中山路的位置和容量，但它不知道中山路高架桥在台风天的实际封闭历史——因为那个信息从来没有被数字化记录。这是陈屿作为滨海市本地人的隐性知识。

Agent 被喂入桥梁抗风等级约束后重跑了模拟。幸存路线从 3 条变成了 1 条（路线 A）。陈屿追加了一个任务令："需要增加两处临时疏散走廊。"

**苏敏的通信韧性流**：

network-resilience-agent 模拟了台风期间通信基站的可能损毁模式，输出了一个"最可能存活"的基站拓扑。

苏敏问了一个 Agent 没有主动提出的问题："如果最坏情况发生——基站损毁超过 70%——卫星通信的接入容量够不够？"

Agent 补充模拟后发现：不够。现有卫星通信容量只能覆盖 40% 的应急通信需求。苏敏在 GHF 中创建了一个新的任务令："设计临时无人机中继网络方案。"

**这里展现的是策元协作的关键机制——并行流之间不需要人手动同步。**
- 何也的水文模型完成后，淹没区数据通过事件总线自动推送给陈屿和方旭
- 陈屿发现桥梁约束后，影响的是自己的疏散流——不需要何也重跑水文模型
- 但季深的工作流（公共信任建模）依赖陈屿的疏散路线——因为市民是否信任疏散指令，取决于路线是否"看起来可行"

---

#### 阶段 3：第一个策元级判断——冲突浮现

六条工作流推进到第三天后，策元核的 orchestration-agent 发出了一个冲突告警：

**方旭的医疗资源分配方案**要求将滨海市的三家大型医院作为"首诊接收点"。但**陈屿的最优疏散路线 A**规划将这三家医院周边道路设为"禁入区"——因为那个区域在模拟中是最先被淹没的。

方旭和陈屿各自的 Agent 都提出了替代方案：
- 方旭的 Agent："将首诊接收点迁移到高地区域的社区医疗站——但容量下降 60%。"
- 陈屿的 Agent："微调路线 A 的终点——绕过医院周边禁入区——但疏散时间增加 18 分钟。"

两个 Agent 在 A2A 通道上交换了方案，做了联合模拟——但结果显示：无论选哪个方案，都会有一个维度的性能不达标。

**这是协议无法解决的冲突。**

策元核触发了策元级评审——所有七个人类成员被拉入一个同步会议（虚拟工作区）。

**这不是"人按是/否"——这是所有智权体的人类部分在讨论价值权衡。**

何也："如果我们接受疏散时间增加 18 分钟——最坏情况下的死亡人数会增加多少？"

方旭的 Agent 和何也的 Agent 在会议期间实时跑了联合模拟："最坏情况下增加约 8%。"

陈屿："如果选社区医疗站方案——哪些伤患会因为没有大型医院设备而得不到救治？"

方旭："重症创伤和需要透析的患者。大约占预计伤患的 15%。"

沉默。

季深开口："还有一个数据——你们的两个方案都假设了市民会服从疏散指令。但公共信任模型显示：如果市民发现疏散终点从三甲医院降级为社区医疗站，信任度预计下降 40%。这意味着实际疏散遵从率可能低于 50%。"

**这个数据改变了权衡的方向。**

最终决定：采用陈屿的方案（增加 18 分钟疏散��间），但方旭需要在禁入区外的两所医院提前部署移动 ICU 模块。

**为什么这是"人+智契"的倍增**：
- Agent 发现了冲突、提出了替代方案、跑了联合模拟——这些没有 Agent 做不到
- 但冲突的解决需要的不是计算——是价值排序：谁的生命更优先？什么样的风险可以接受？
- 季深的介入改变了整个方向——因为公共信任这个维度是 Agent 模拟不出来的（Agent 可以模拟趋势，但不能判断"40% 下降意味着什么"）
- 最终方案不是 AB 二选一——是人想出了一个第三种路径（移动 ICU 部署）

---

#### 阶段 4：集成验证——Agent 的端到端压测

各子系统的方案就绪后，策元核触发集成测试。

orchestration-agent 将所有子系统的模型拼接成一个端到端模拟：台风路径 → 水文淹没 → 通信损毁 → 疏散执行 → 医疗响应 → 公共信任反馈。

模拟跑了 1,000 次。每次使用不同的台风参数、不同的损毁分布、不同的市民行为模式。

**结果**：在 95% 的模拟中，系统表现符合 G4 Gate 的验收标准。但在 5% 的极端场景中——台风路径比历史最坏情况偏北 3 度——出现了级联失败：通信损毁导致疏散指令无法送达 → 市民自行疏散路径与规划路径冲突 → 医疗资源无法定位伤患。

**为什么这是 Agent 的能力展示**：1,000 次端到端模拟涉及 6 个子系统的交互——如果靠人类手动对接，这根本不可行。Agent 不仅能跑模拟，还能自动识别出"5% 的极端场景"是系统性弱点而非随机波动。

---

#### 阶段 5：人的最终判断——什么是"足够好"？

策元核将集成测试报告推送给全体成员，附带一个自动生成的建议："系统在 95% 场景下达标。建议：接受当前方案，对 5% 极端场景启动独立任务令——'极端场景预案设计'。"

苏敏看了通信损毁数据，说："那个 5% 的极端场景本质上是一个问题——通信完全中断后的 Plan B。我可以在两周内设计一个离线模式方案——利用 CONC 的断网缓存协议，让市民终端在无网络时自动切换到 P2P 广播。"

季深说："但即使有了 Plan B，那个场景下的人的行为模型也不一样——没有通信时，市民会做完全不同的决定。我的模型需要重新校准。"

**最终决策不是"通过/不通过"——而是一组人的判断的综合**：

1. 当前方案对 95% 场景已足够，先行提交（Gate 判定：PASS）
2. 5% 极端场景作为"已知残余风险"记录在 GHF 中
3. 苏敏的离线模式和季深的无通信行为模型作为 v2.0 迭代任务

**为什么这必须是人来做**：Agent 可以计算"95% 的达标率是多少"——但它不知道"95% 够不够"。这个判断取决于滨海市政府对风险的容忍度、预算、和项目截止日期——所有这些都是 Agent 无法获取的上下文。

---

#### 阶段 6：交付与持续反馈——人的角色从"设计者"转为"观察者"

方案提交给滨海市政府后，方旭和周敏被指定为"持续反馈通道"——他们不参与 v2.0 的迭代设计，而是负责收集实际台风季节的系统表现数据，通过 GHF 事件表反馈给策元。

**三个月的真实运转后**：

一场真实台风验证了系统的核心设计——疏散在 95% 的预测范围内顺利完成。但一个意料之外的事件发生了：台风过境后的第三天，滨海市南部爆发了次生洪水——这不在原始水文模型里，因为它来自上游水坝的紧急泄洪，而非直接降雨。

周敏的 Agent 在 GHF 中记录了事件：`UNMODELED_EVENT_TYPE=upstream_dam_release`。

策元自动创建了一个新的任务令，推送给何也："水文模型需扩展——纳入上游水利设施的影响。"

**闭环**：协作没有结束。交付只是下一个迭代的开始。而这个迭代的触发不需要人主动发起——GHF 中的异常事件被 Agent 自动识别并转化为任务令。

---

### 4.3 总结：六个阶段的协作结构

| 阶段 | 主导者 | 关键协议机制 | 人做了什么 Agent 做不了的 |
|------|--------|-------------|------------------------|
| 1. DAG 拆解 | Agent（策元核） | 编排 API | 设定项目的战略优先级和约束边界 |
| 2. 并行探索 | 各智权体 Agent 群 | 事件总线自动同步 | 陈屿的桥梁抗风知识（隐性经验）；苏敏的"最坏情况足够吗"（风险意识） |
| 3. 冲突解决 | **全员人类** | A2A 协商 + 策元级评审 | 价值权衡——"增加 18 分钟 vs 降级医疗站"是无最优解的；季深引入公共信任维度改变讨论方向 |
| 4. 集成验证 | Agent | 端到端模拟 + Gate 判定 | — |
| 5. 最终决策 | **全员人类** | GHF 记录残余风险 | "95% 够不够"——这是政治判断不是工程判断 |
| 6. 持续反馈 | 事件驱动 | GHF 事件表 + 自动任务令生成 | 周敏识别"次生洪水不在模型里"——这是对现实世界意外事件的命名能力 |

## 五、从设计到小说：写作指南

### 5.1 核心原则：展现"收敛循环"，而非"人做了判断"

| 不好的写法 | 好的写法 |
|-----------|---------|
| "林屿判断出这是已知设计特性。" | 展现诊断报告的三个异常聚类 → 林屿看到"峰值型与市场结算 p=0.94"→ 想起两年前协议设计中讨论过的 Gossip 延迟特性 → 说"峰值型先不管"。 |
| "陈屿发现桥梁约束后推翻了路线。" | 展现 Agent 的 50 万次蒙特卡洛模拟 → 三条推荐路线 → 陈屿看到"路线 B 经过中山路"→ 他脑子里浮现台风天中山路高架桥封闭的画面 → 他输入桥梁抗风等级约束 → 路线从 3 条变成 1 条。 |
| "策元级会议解决了冲突。" | 展现 A2A 通道上的替代方案交换 → 两个方案数据都不达标 → 会议室沉默 → 季深开口说公共信任下降 40% → 所有人意识到这不是工程问题 → 方旭突然说"移动 ICU"→ 何也的 Agent 现场验证可行。 |

### 5.2 五个可复用的叙事节奏模式

**模式 1：Agent 先跑，人后看**
- Agent 生成海量输出（诊断报告、模拟结果、候选方案）
- 人在其中寻找"异常点"——不是审查全部，而是凭直觉找到"哪里不对劲"
- 这个"不对劲"就是判断力的入口

**模式 2：人提出"如果……"——Agent 计算后果**
- 人提出一个假设性问题（"如果最坏情况呢？""如果桥梁封闭呢？"）
- Agent 快速模拟验证——数量级远超人类能力
- 人根据模拟结果做出方向判断

**模式 3：Agent 说"两个方案都不行"——人找第三条路**
- Agent 在现有约束下找不到最优解
- 人在讨论中引入一个 Agent 没有计算过的维度（公共信任、道德风险、政治可行性）
- 这个新维度改变了对"好"的定义 → 第三条路出现

**模式 4：Agent 做到了 95%——人决定这够不够**
- Agent 完成了端到端验证，给出了精确的达标率
- 人面对的不是"对/错"——是"足够好/还不够"
- 这个判断需要的不是计算力——是对"这个世界需要什么"的理解

**模式 5：人命名异常——Agent 将之转化为任务**
- 真实世界出现了一个未被模型覆盖的事件
- 人识别出它的独特性并命名（"次生洪水""上游泄洪"）
- Agent 自动将命名的事件转化为新的任务令
- 命名——这个动作本身——是人类认知不可替代的核心

### 5.3 Agent 对话的写法建议

**避免**：让 Agent 说"根据我的分析……""我建议……"——听起来像低配秘书。

**推荐 **：Agent 的对话是**高密度信息压缩**——像是在 3 秒内读了一篇 50 页的技术报告。Agent 不是"说话"，是"投放结构化认知对象"。

**示例**：

> 诊断报告在她视野里展开——不是文字，是三簇光点。金色的是峰值型，蓝色的是脉冲型，红色的是级联型。每簇背后挂着一个数字：p=0.94，p=0.31，节点 ID。
>
> "市场结算周期，"林屿说，"这不是异常。这是已知噪声。"
>
> 她挥手抹掉金色光点。
>
> 诊断 Agent 没有反驳。它知道市场结算周期是什么——但它不知道在"寻找安全漏洞"的上下文里，一个 p=0.94 的相关性意味着"安全地忽略"而不是"继续深挖"。那个边界是林屿给的。
