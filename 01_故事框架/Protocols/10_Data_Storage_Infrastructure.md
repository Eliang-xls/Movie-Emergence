# CONC 数据存储与载体架构
## Distributed Data Infrastructure — Where Everything Lives

> *"企业通过云服务器存放所有信息。策元的工作产出——文档、报告、代码、记录——存放在什么载体上？"*

---

## 〇、核心原则：没有"CONC 服务器"

传统企业：所有数据 → 企业云（Google Drive / SharePoint / AWS S3）→ 员工通过客户端访问。

CONC：**没有中心服务器。每个智权体的 Agent 是数据存储节点。数据通过去中心化协议在节点间同步。**

```
企业模式:   [服务器] ← 所有员工从这里读写
CONC 模式:  [Agent A 本地] ⇄ [Agent B 本地] ⇄ [Agent C 本地]
                 ↕                ↕                ↕
            [IPFS 永久层]   [Git 版本层]    [CRDT 状态层]
```

---

## 一、数据分类与存储载体

策元运转中产生的数据分为五类——各有其最佳存储载体：

| 数据类型 | 特征 | 存储载体 | 现有技术 |
|---------|------|---------|---------|
| **版本化资产** | 代码、文档、设计稿——频繁变更、需协作 | 策元 Git 仓库 | Git + Git LFS |
| **不可变记录** | PCP 协议、验收报告、会议录像——写入后不改 | IPFS 内容寻址存储 | IPFS / Filecoin |
| **分布式状态** | 任务令状态、CCR 数值、NR 分数——多节点需一致 | CRDT 状态层 | OrbitDB / GunDB |
| **实时通信** | 策元内聊天、会议——短暂、高频 | Matrix 协议 | Matrix / Jitsi |
| **个人私密数据** | 个人创意草稿、私钥——仅自己可见 | Agent 本地加密存储 | 本地文件 + 加密 |

## 二、逐类详述

### 2.1 版本化资产 → 策元 Git 仓库

**每个策元在创建时自动初始化一个 Git 仓库。** 这是策元所有可版本化资产的"单一真相源"。

```
策元 "OpenDesign" 的仓库结构：

opendesign.conc/                 # 策元根目录（每个成员 Agent 本地都有完整克隆）
├── CONC_PCP.md                  # 预共识协议（策元宪法）
├── CONC_SEED.md                 # 创意图元（策元起源）
├── CONC_ROSTER.md               # 当前成员名册 + NR
├── src/                         # 源代码
├── docs/                        # 文档
│   ├── architecture/
│   ├── meeting-notes/           # 会议纪要
│   └── decisions/               # 策元核决策记录
├── designs/                     # 设计稿（Git LFS）
├── tasks/                       # 任务令跟踪
│   └── TW-001..TW-099/         # 每个任务令一个目录
│       ├── specification.md     #   任务令规格
│       ├── deliverables/        #   交付物
│       └── review/              #   PEER 评审记录
└── releases/                    # 发布版本
```

**同步机制**：Agent 自动执行 `git pull/push`——每当智权体提交任务令成果时，Agent 推送至其他成员的 Agent。类比如今的开源项目——没有"GitHub 服务器"，每个开发者本地有完整仓库，通过 Git 协议同步。

### 2.2 不可变记录 → IPFS 内容寻址存储

**写完就不会再改的数据——存放在 IPFS 上，获得永久的、内容寻址的 CID。**

| 记录类型 | 何时写入 IPFS | 作用 |
|---------|-------------|------|
| PCP 协议快照 | 策元创建时 + 每次修订时 | 策元宪法的不可篡改版本 |
| PEER 评审报告 | 每次评审完成后 | 验收的不可抵赖证明 |
| 会议录像 | 每次策元会议结束后 | 决策过程的永久记录 |
| 任务令完成快照 | 任务令 MERGED_RESOLVED 时 | 贡献的永久证据 |
| 策元分裂记录 | 分叉时 | 分支历史的完整链 |

**寻址方式**：CCR 和 NR 数据中不存文件内容——只存 IPFS CID（内容哈希）。任何节点可通过 CID 从 IPFS 网络检索原始文件。

```
例：任务令 TW-042 的验收记录

{
  "task_warrant_id": "TW-042",
  "status": "MERGED_RESOLVED",
  "verification_protocol": "PEER_3",
  "review_records_cid": "ipfs://QmXxx...abc",   ← 3份评审报告在IPFS上
  "deliverables_cid": "ipfs://QmYyy...def",      ← 交付物快照在IPFS上
  "timestamp": "2026-07-15T14:30:00Z"
}
```

### 2.3 分布式状态 → CRDT 状态层

**任务令状态、CCR、NR——这些数据需要多节点实时一致。** 但不能用中心化数据库——需要用 CRDT（Conflict-free Replicated Data Type）。

| 状态数据 | CRDT 类型 | 同步方式 |
|---------|:------:|---------|
| 任务令当前阶段（BROADCAST→EXECUTING→...） | LWW-Register（最后写入胜出） | Agent 间 Gossip |
| CCR 贡献-消费比 | G-Counter（只增计数器） + 时间衰减 | 每 6 小时同步 |
| NR 声誉分数 | G-Counter（贡献） - G-Counter（衰减） | 每次任务令完成后更新 |
| 策元成员名册 | OR-Set（观察删除集合） | 加入/退出时广播 |

**为什么 CRDT 而非区块链**：CRDT 不需要全局共识——两个节点可以独立更新，合并时自动解决冲突。比特币需要全局共识（防止双花），但 CONC 的 CCR/NR 更新是**单节点发起的增量操作**——不需要全网共识，只需要最终一致。

### 2.4 实时通信 → Matrix 协议

策元内的聊天、讨论——使用 Matrix（去中心化通信协议）。每个策元有一个 Matrix 房间。消息历史分布在各成员的 homeserver 上——不依赖单一服务器。

### 2.5 个人私密数据 → Agent 本地加密

创意草稿、私钥、未发布的创意图元——仅在智权体自己的 Agent 本地存储，端到端加密。Agent 在发布前不上传任何内容。

## 三、一个新智权体加入策元时如何获取全量数据

```
智权体 D 加入策元 "OpenDesign"：

1. Agent D 向策元现有成员的 Agent 请求 Git 仓库地址
2. Agent D 执行 git clone → 获取所有版本化资产（代码、文档、设计稿）
3. Agent D 向网络请求该策元的 CRDT 状态层 → 获取所有任务令当前状态
4. Agent D 通过 CCR 中记录的 IPFS CID → 检索 IPFS 网络 → 获取所有历史记录
5. Agent D 加入策元的 Matrix 房间 → 获取聊天历史

完成——Agent D 现在拥有策元的完整数据副本，可以开始协作。
```

**这与 Git 克隆一个仓库然后可以离线工作是完全相同的模式。**

## 四、数据持久性：策元解散后数据去哪了

| 策元解散后... | 数据的去向 |
|-------------|----------|
| Git 仓库 | 保留在所有曾经克隆过的 Agent 本地。只要有 ≥1 个 Agent 保留，仓库就存活 |
| IPFS 记录 | 只要 IPFS 网络上有 ≥1 个节点 pin 了这些 CID，数据就永久可检索 |
| CRDT 状态 | 最终一致性——最终所有 Agent 的状态收敛到"策元已解散" |
| Matrix 聊天 | 保留在成员的 homeserver 上——可查阅但不再活跃 |

**关键**：没有中心服务器被"关闭"——数据不会消失。只要有人保留着，它就在。**这类似于 BitTorrent——只要有人做种，文件就活着。**

## 五、存储成本：谁来承担？

| 数据类型 | 存储成本承担者 |
|---------|-------------|
| Git 仓库 | 每个克隆的 Agent 用自己的磁盘空间存储——类似今天你用 Git 克隆一个开源项目 |
| IPFS 记录 | 策元成员共同 pin 关键 CID（PCP、验收记录）——IPFS pinning 服务的费用从策元公共基金支付 |
| CRDT 状态 | 轻量（纯文本 + 数字），存储成本可忽略 |
| Matrix 聊天 | 各成员的 Matrix homeserver（可以是自托管或公共实例） |

**与企业的差异**：企业每月付 AWS 账单集中存储。CONC 中每个智权体承担自己那份存储——分布式成本。一个 100 人策元的 Git 仓库（含 LFS 设计稿）可能在 5-50GB——存在每个成员的本地磁盘上，总冗余 100×，但每个个体成本很低。

---

## 六、核心陈述

> **策元的工作产出不存放在任何"CONC 服务器"上。代码和文档在 Git 仓库中（每个成员 Agent 本地都有完整克隆）。验收报告和会议录像在 IPFS 上（内容寻址，永久可检索）。任务令状态和 CCR/NR 通过 CRDT 在节点间实时同步。聊天在 Matrix 上。私密创意在 Agent 本地加密。**

> **一个新成员加入策元 = Git clone + CRDT 状态同步 + IPFS 检索 + Matrix 加入。策元解散时，只要还有一个 Agent 保留着数据，它就活着。没有中心服务器可以"关闭"——数据是分布式的，如同 BitTorrent。**
