## 框架核心架构

### 一、从企业体系中"升维吸收"而非推倒重来

我调研了四套企业体系并做了 CONC 适配：

| 企业体系 | 吸收什么 | 去掉什么 |
|---------|---------|---------|
| **ISO 15489 记录管理** | 文档生命周期六阶段 + 元数据标准 | 中心化 DMS |
| **FDA 设计控制 (21 CFR 820)** | 五级 Gate 门控 + DHF 审计追踪 | "上级审批"，替换为 PEER 验证 |
| **PLM 产品生命周期管理** | BOM→MOC 模块清单 + ECN→CR 变更控制 | 供应商层级管理 |
| **ECM 企业内容管理** | 分类法 + 全文搜索 + 审计追踪 | 中心化存储 |

**核心产出：策元历史文件（GHF）**——对标企业的设计历史文件（DHF），自动记录策元从创建到解散的全部决策、评审、变更和验证。

### 二、Agent = 知识引擎，不是"智能文件柜"

Agent 相比比特币节点的质变在于：它具备**四层记忆系统**（感觉→短期→工作→长期）和**文档智能处理流水线**（格式校验→自动分类→元数据附加→知识提取→索引更新→通知同步）。

关键技术选型：
- **语义搜索**：本地嵌入模型 (nomic-embed-text) + SQLite-vec 向量数据库
- **知识图谱**：实体-关系图谱，支持"谁做过什么""任务令上下游"等查询
- **RAG 三层架构**：策元内 RAG → 跨策元 RAG → 全网 RAG

### 三、Token 成本控制的分级推理策略

```
确定性操作（零 Token）→ 本地小模型（零边际）→ 缓存复用 → 云端大模型（最后手段）
```

日均 Token 预算约 8500 tokens，成本 $0.09-0.51/天。65% 操作由本地模型覆盖，30% 命中缓存，仅 5% 需要云端调用。

### 四、策元仓库标准化结构

借鉴企业的项目目录规范 + Git Flow，定义了八大文档分类（治理/创意/设计/执行/验证/变更/通信/知识），配合 Git hooks 实现自动化文档流程。

### 五、五级协议门控

| Gate | 名称 | 验证方式 | 对标企业 |
|------|------|---------|---------|
| Gate 0 | 聚结门 | AUTO | 立项评审 |
| Gate 1 | 计划门 | PEER(3) | 设计输入评审 |
| Gate 2 | 拆解门 | AUTO + AI | 设计输出评审 |
| Gate 3 | 交付门 | PEER(3) + AUTO | 设计验证 |
| Gate 4 | 发布门 | PEER + 消费者 | 设计确认 |
