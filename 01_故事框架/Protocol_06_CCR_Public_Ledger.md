# CONC CCR 公开账本协议规范
## Contribution-to-Consumption Ratio Public Ledger Specification v1.0

> **定位**: CCR 公开账本是 CONC 反搭便车机制的核心基础设施。它使每个智权体的贡献-消费比率全网可见，将搭便车行为从"经济上不可见"变为"声誉上可见"——不施加直接惩罚，但通过协议权重差异制造结构性激励。
>
> **响应**: 协议完备性审计中 CCR 被评为 🔴 仅概念 (10%)。本规范将其补全至正式协议规范。
>
> **依赖**: 身份层 (Identity Layer) — 智权体注册；价值层 (Value Layer) — VT/NR/ALP 事件流；策元层 (Genesis Layer) — 任务令生命周期事件。

---

## 零、设计原则

1. **比率公开，绝对量隐藏**: CCR 公开的是 VT/CU 的比值和小数点后两位精度。绝对 VT 总额和 CU 总额不直接公开——仅通过 CCR 间接可感知。这保护智权体的经济隐私，同时让声誉信号可被审计。
2. **贡献质量加权**: 并非所有 VT 同等计算。PEER 评审质量分、任务令验证模式、NR 转移税折扣——这些维度影响有效 VT 的计算。
3. **时间衰减**: 近期活动权重高于远期活动。一个两年前高贡献但近期沉默的智权体，其 CCR 应低于近期持续贡献但总量较低的智权体。
4. **消费透明**: CU 消费来源可追溯——基础 CU 分配、ALP 借贷、工具使用——每个智权体的消费结构在账本上可见（但具体金额隐藏）。
5. **可验证性优先**: 所有 CCR 计算输入均可被第三方独立验证。CCR 不是"信任分数"——它是可复现的计算结果。

---

## 一、数据模型

### 1.1 VT 贡献来源 (Contribution Sources)

每个智权体的有效 VT 贡献 $VT_{eff}(n)$ 由以下来源加权求和：

| 来源 | 符号 | 原始值 | 质量权重 | 说明 |
|------|:----:|--------|:-------:|------|
| 任务令完成 | $VT_{task}$ | 任务令 reward_vt | $q_{task} \in [0, 1]$ | PEER 评审质量分归一化 |
| PEER 评审工作 | $VT_{review}$ | 评审 VT 奖励 | $q_{review} \in [0, 1]$ | 评审一致性加权（评审结果与最终共识的偏差） |
| NR 转移接收 | $VT_{nr\_recv}$ | 接收的 NR 量 | $1 - \tau_{nr}$ | $\tau_{nr} = 0.30$ 为 NR 转移税——接收 NR 仅 70% 计入 CCR |
| 特殊贡献 | $VT_{special}$ | PCP 定义的特殊贡献 VT | $q_{special} \in [0, 1]$ | 策元核特别认定的突破性贡献 |

**有效 VT 计算公式**:

$$VT_{eff}(n, t) = \sum_{i \in \text{events}(n, t)} w_i \cdot VT_i$$

其中 $w_i$ 为事件 $i$ 的综合权重：

$$w_i = q_{quality}(i) \times d_{decay}(i) \times m_{mode}(i)$$

| 权重因子 | 含义 | 取值范围 |
|---------|------|:------:|
| $q_{quality}(i)$ | 质量权重 | $[0, 1]$ |
| $d_{decay}(i)$ | 时间衰减权重 | $[0, 1]$ |
| $m_{mode}(i)$ | 验证模式权重 | $\{1.0, 0.8, 0.6\}$ |

**验证模式权重 $m_{mode}$**:

| 验证模式 | $m_{mode}$ | 理由 |
|---------|:--------:|------|
| AUTO（自动化测试验证） | 1.0 | 完全客观——最高可信度 |
| PEER（同行评审） | 0.8 | 统计收敛但存在评审者偏差风险 |
| MARKET（市场反馈验证） | 0.6 | 信号噪声最高（$\sigma^2_v = 0.25$）——最低可信度 |

> **设计理由**: 模型三（NR 信号博弈）证明，MARKET 验证模式的信号噪声远高于 AUTO 模式。CCR 通过验证模式权重反映这一差异——防止智权体通过大量低质量 MARKET 型任务令维持虚高 CCR。

**质量权重 $q_{quality}$**:

- **PEER 型任务令**: $q_{quality} = \text{avg}(\text{peer\_scores}) / 5.0$（假设 5 分制评审）
- **AUTO 型任务令**: $q_{quality} = 1.0$（通过即满分——AUTO 为二元判定）
- **MARKET 型任务令**: $q_{quality} = \min(1.0, \text{metric\_achieved} / \text{metric\_target})$（实际达成/目标值）
- **PEER 评审工作**: $q_{review} = 1.0 - |\text{reviewer\_score} - \text{consensus\_mean}| / 5.0$（评审偏离共识的程度——偏离越大权重越低）
- **边界情况**: $q_{quality} = 0$ 的任务令（PEER 全 0 分、MARKET 达成 0%）不计入 VT 贡献但会计入任务令计数（用于反刷分检测）

### 1.2 CU 消费来源 (Consumption Sources)

每个智权体的总 CU 消费 $CU_{total}(n)$ 由以下来源组成：

| 来源 | 符号 | 计算方式 | 说明 |
|------|:----:|---------|------|
| 基础 CU 分配 | $CU_{base}$ | 定额 100 CU/周期 | 每个注册智权体的基础计算资源配额 |
| ALP 借贷 | $CU_{alp}$ | 借贷 stablecoin 等值 CU | 按协议内稳定币汇率折算 |
| 工具使用 | $CU_{tool}$ | 实际工具调用计费 | AI 模型调用、云计算资源、工厂生产订单 |
| 策元资源消耗 | $CU_{genesis}$ | 策元内共享资源的分摊 | 按策元成员数均摊 |
| 公共物品注入 | $CU_{public}$ | 外部公共 CU 分配 | 基金会/政府/社区的公共 CU 注入——不计入个人 CCR（避免扭曲） |

**有效 CU 计算公式**:

$$CU_{eff}(n, t) = CU_{base}(n, t) + CU_{alp}(n, t) + CU_{tool}(n, t) + CU_{genesis}(n, t)$$

> **$CU_{public}$ 不计入**: 公共 CU 注入（如社区无偿提供的算力资源）不增加消费侧的 CU 分母——否则接受公共资源的智权体会被惩罚。这是对搭便车检测的精确化：只计算"消耗了他人创造的价值"的部分。

**CU 的折算标准**:

| 消费类型 | 折算单位 | 1 CU 等价于 |
|---------|---------|-----------|
| 基础分配 | 协议定额 | — |
| ALP 借贷 | stablecoin | 1 stablecoin = 1 CU |
| AI 模型调用 | token 数 | 10K tokens (GPT-4 级别) = 1 CU |
| 云计算 | vCPU-hour | 1 vCPU-hour = 2 CU |
| 工厂生产 | 生产工时 | 1 机器小时 = 5 CU |

### 1.3 CCR 公式

#### 时间衰减模型

时间衰减采用指数衰减函数：

$$d_{decay}(t, t_{event}) = e^{-\lambda_d \cdot (t - t_{event})}$$

其中 $\lambda_d$ 为衰减速率，对应半衰期 $T_{1/2} = \ln(2) / \lambda_d$。

| 参数 | 默认值 | 含义 |
|------|:-----:|------|
| $\lambda_d$ | $0.0038$ day$^{-1}$ | 日衰减速率 |
| $T_{1/2}$ | 180 天 (~6 个月) | VT 贡献的半衰期 |

> **与 NR 衰减的区别**: NR 衰减（23 个月半衰期）服务于长期声誉追踪。CCR 衰减（6 个月半衰期）服务于近期行为信号——CCR 回答"这个智权体现在是净贡献者还是净消费者"，NR 回答"这个智权体历史上积累了多少信任"。

#### 核心公式

##### 瞬时 CCR

$$CCR_{instant}(n, t) = \frac{\sum_{i \in \text{events}(n)} VT_i \cdot q_i \cdot m_i \cdot e^{-\lambda_d (t - t_i)}}{\sum_{j \in \text{consumption}(n)} CU_j \cdot e^{-\lambda_d (t - t_j)}}$$

其中：
- $VT_i$ = 事件 $i$ 的原始 VT 值
- $q_i$ = 事件 $i$ 的质量权重
- $m_i$ = 事件 $i$ 的验证模式权重
- $t_i$ = 事件发生时间戳
- $CU_j$ = 消费事件 $j$ 的 CU 值

##### 边界处理

当 $CU_{eff}(n, t) = 0$ 时（新注册、尚未消费）：

$$CCR_{instant} = VT_{eff} / \max(CU_{eff}, CU_{base\_min})$$

其中 $CU_{base\_min} = 10$（防止除零——新智权体即使未消费也有一个最小分母，避免无限大 CCR）。

等价于：新智权体在开始消费前，其 CCR 反映了纯粹的贡献状态——但不会因为分母为零而发散。

#### 聚合窗口 CCR

除瞬时 CCR 外，协议同时计算两个滑动窗口聚合值：

| 窗口 | 计算方式 | 用途 |
|------|---------|------|
| CCR_30d | 过去 30 天内的 $VT_{eff}$ 总和 / 过去 30 天内的 $CU_{eff}$ 总和 | 短期趋势——检测近期行为变化 |
| CCR_90d | 过去 90 天内的 $VT_{eff}$ 总和 / 过去 90 天内的 $CU_{eff}$ 总和 | 中期趋势——平滑短期波动 |

> **窗口 CCR 不使用指数衰减**——窗口内的所有事件等权计算。窗口边界是硬截止。这使窗口 CCR 更直观可理解（"过去 30 天赚了多少/花了多少"）。

#### CCR 趋势 (Trend)

CCR 趋势用于描述智权体的发展方向：

$$CCR_{trend} = \frac{CCR_{30d} - CCR_{90d}}{CCR_{90d}}$$

| $CCR_{trend}$ | 标签 | 含义 |
|:---:|------|------|
| $> 0.20$ | 📈 strongly_improving | 近期贡献显著增加或消费显著减少 |
| $(0.05, 0.20]$ | ↗️ improving | 贡献在增长中 |
| $[-0.05, 0.05]$ | ➡️ stable | 贡献-消费比稳定 |
| $[-0.20, -0.05)$ | ↘️ declining | 贡献在下降或消费在增加 |
| $< -0.20$ | 📉 strongly_declining | 需要关注——可能正在滑向搭便车 |

## 二、隐私边界

### 2.1 三层次可见性模型

```
┌─────────────────────────────────────────────────────────────┐
│  层次三：CCR 公开层 (Public)                                  │
│  · CCR 比值（精确到小数点后两位）                              │
│  · CCR 趋势标签 (improving / stable / declining)             │
│  · CCR 百分位排名                                            │
│  · VT 贡献类别分布（任务令 % / PEER % / NR接收 %）             │
│  · CU 消费类别分布（基础 % / ALP % / 工具 % / 策元 %）         │
│  · 活跃策元列表                                               │
│  可见范围: 全网所有智权体 + 未注册观察者                        │
├─────────────────────────────────────────────────────────────┤
│  层次二：聚合层 (Aggregated — 策元内可见)                      │
│  · 30d/90d VT 聚合值（非逐笔）                                │
│  · 30d/90d CU 聚合值（非逐笔）                                │
│  · 任务令完成数、评审完成数、平均质量分                          │
│  · PEER 评审一致性评分                                        │
│  可见范围: 同策元成员 + 潜在策元（sim ≥ θ 的意向表达者）        │
├─────────────────────────────────────────────────────────────┤
│  层次一：交易层 (Pseudonymous — 仅自己 + 审计)                 │
│  · 逐笔 VT 交易记录（任务令 ID、金额、时间戳）                  │
│  · 逐笔 CU 消费记录（消费类型、金额、时间戳）                   │
│  · ALP 借贷明细（金额、利率、还款状态）                         │
│  · NR 转移记录（转出/转入、转移税扣除）                         │
│  可见范围: 智权体自己 + 随机审计委员会（争议时）                │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 隐私设计原则

1. **CCR 是比率——不是绝对量**: 公众知道某智权体的 CCR = 3.42，但不知道这是从 3420 VT / 1000 CU 还是从 34.2 VT / 10 CU 计算得出。比率隐藏了绝对规模。

2. **百分比而非绝对值**: 类别分布以百分比形式公开（"任务令占 VT 贡献的 75%"），而非绝对 VT 值。这使公众可以感知贡献结构，但不能推断经济规模。

3. **伪名非匿名**: 智权体 ID（ns_xxxxxxxx）是公开标识符。协议不承诺完全匿名——CCR 公开账本本身就是一种"实名化"机制。但智权体 ID 与现实身份的绑定是**自愿的**——智权体可以选择不公开将自己的 ns_id 与现实身份关联。

4. **审计委员会的安全飞地**: 争议仲裁时，审计委员会（随机抽取的 PEER 评审者 + 策元核代表）可在有限时间窗口内查看逐笔交易——但审计日志被记录（谁在何时查看了谁的交易明细）。

5. **退出时的数据处置**: 
   - 友好退出 (amicable exit): 30d/90d 聚合值保留——CCR 归档但不删除。历史 CCR 作为公共记录。
   - 标准退出 (standard exit): 同友好退出。
   - 争议退出 (disputed exit): 全部交易记录在审计窗口期内对仲裁委员会开放。

### 2.3 隐私的已知局限

| 局限 | 风险 | 缓解 |
|------|------|------|
| 从 CCR + 类别百分比可反向推断绝对量范围 | 如果攻击者知道某类消费的单位 CU 成本，可推断总消费规模 | 类别百分比四舍五入到 5% 精度（而非精确百分比） |
| 活跃策元列表可推断社会图 | 可推断智权体的协作网络 | 策元成员列表本就是公开信息（策元层数据）——CCR 不增加额外信息泄露 |
| 时间序列分析可推断收入波动 | 长期观察 CCR 变化可推断经济状况变化 | 这是 CCR 的**设计意图**——公开账本就是用于感知行为变化；但具体金额不可见 |
| 审计委员会可能泄密 | 仲裁时查看的交易明细可能被审计者泄露 | 审计委员会成员签署协议承诺；泄密行为导致 NR 扣减 |

**字段说明**:

| `ccr.window_90d` | float | 过去 90 天 CCR（等权聚合） |

| `ccr.trend.label` | string | 趋势标签 |
| `ccr.percentile_rank` | float | 全网百分位排名 (0.0 = 最低, 1.0 = 最高) |

| `consumption_breakdown` | object | CU 消费来源的百分比分布（四舍五入到 5%） |
| `activity_summary` | object | 聚合活动统计 |
| `linked_scores` | object | 关联的协议层指标（NR、ALP、阻尼系数） |
| `damping_multiplier` | float | 反垄断阻尼系数的 CCR 调节因子 |

```json

  "archived_ccr": 2.15, "departed_at": "2025-11-01T00:00:00Z" }
```

### 3.2 GET /ccr/{ns_id}/history

获取智权体 CCR 的时间序列历史。

**请求**:
```
GET /ccr/ns_0a1b2c3d/history?window=90d&granularity=7d
```

| 参数 | 默认 | 说明 |
|------|:---:|------|
| `window` | `90d` | 查询窗口: `30d`, `90d`, `180d`, `365d`, `all` |
| `granularity` | `7d` | 数据粒度: `1d`, `7d`, `30d` |

**响应**:
```json
{
  "ns_id": "ns_0a1b2c3d",
  "history": [
    { "date": "2026-05-14", "ccr_instant": 3.42, "ccr_30d": 4.15, "ccr_90d": 3.28 },
    { "date": "2026-05-07", "ccr_instant": 3.18, "ccr_30d": 3.90, "ccr_90d": 3.20 },
    ...
  ]
}
```

### 3.3 GET /ccr/leaderboard

获取 CCR 排名榜单。

> **治理开关**: 榜单功能可由社区治理投票关闭（默认开启）。关闭后返回 403 `LEADERBOARD_DISABLED_BY_GOVERNANCE`。

**请求**:
```
GET /ccr/leaderboard?top=20&filter=active_30d&include_trend=true
```

| 参数 | 默认 | 说明 |
|------|:---:|------|
| `top` | `20` | 返回前 N 名 (最大 100) |
| `filter` | `all` | `all`（全部智权体）, `active_30d`（过去 30 天有活动）, `active_90d` |
| `sort_by` | `ccr_instant` | `ccr_instant`, `ccr_30d`, `ccr_90d` |
| `include_trend` | `false` | 是否包含 CCR 趋势 |

**响应**:
```json
{
  "leaderboard": [
    {
      "rank": 1,
      "ns_id": "ns_x9y8z7w6",
      "ccr_instant": 8.91,
      "ccr_30d": 9.50,
      "trend_label": "stable",
      "activity_summary": {
        "active_genesis_units": 3,
        "tasks_completed_30d": 15
      }
    },
    ...
  ],
  "generated_at": "2026-05-14T22:00:00Z",
  "total_ranked": 1284,
  "filter_applied": "active_30d"
}
```

**边界处理**:

- `filter=active_30d` 过滤掉过去 30 天内无任何 VT 或 CU 事件的智权体。
- 榜单仅包含 `percentile_rank >= 0.5`（即排名前 50%）的智权体——避免对低 CCR 智权体的公开羞辱（榜单不是"耻辱榜"）。
- 新注册智权体（注册 < 14 天）自动排除——防止新进入者因基础 CU 分配而出现在低排名位置。

## 四、与协议栈的集成

### 4.1 任务令匹配优先级

CCR 影响三阶段任务令分配中的**匹配优先级**：

| CCR 区间 | 匹配权重调整 | 说明 |
|---------|:---------:|------|
| CCR ≥ 3.0 | +15% 权重 | 高贡献者获得略高的任务令推荐优先级 |
| 1.0 ≤ CCR < 3.0 | 0% 权重（基线） | 标准匹配 |
| 0.5 ≤ CCR < 1.0 | -10% 权重 | 略有降低——但仍可承接任务令 |
| CCR < 0.5 | -30% 权重 | 显著降低——任务令系统优先推荐给其他匹配者 |

> **非惩罚性质**: CCR 低不是禁止承接任务令。任务令仍对所有人开放——CCR 仅影响推荐算法的排序。一个低 CCR 但能力高度匹配的智权体仍可在 Step 3（外源溢出）中承接未被认领的任务令。

**与 NR 的交叉效应**:
- 任务令匹配的综合优先级 = 0.4 × CCR_score + 0.4 × capability_match + 0.2 × NR_score
- CCR 和 NR 各占 40% 权重——保持平衡，不让单一指标主导

### 4.2 策元核选举权重

在策元核轮值选举中，CCR 作为候选者权重的组成部分：

$$W_{core\_candidate}(n) = 0.50 \times \frac{NR(n)}{\max(NR)} + 0.30 \times \frac{CCR(n)}{\max(CCR)} + 0.20 \times \frac{Tenure(n)}{\max(Tenure)}$$

其中 Tenure(n) 为智权体在当前策元的连续成员时长。

> **CCR 不是决定性因素**——NR 仍占 50% 权重（因其更长期稳定）。CCR 占 30% 反映近期贡献行为。策元资历占 20% 防止"新来的明星"立即掌握策元核。

### 4.3 争议仲裁中的预设

在争议仲裁中，CCR 影响**初始举证责任分配**：

| 场景 | 高 CCR 方 (≥ 3.0) | 低 CCR 方 (< 0.5) |
|------|:---:|:---:|
| 任务令质量争议 | **有利预设** — 假定交付物达到标准，对方需举证瑕疵 | **不利预设** — 需自证交付物质量 |
| 回报分配争议 | **有利预设** — 假定 VT 分配与其贡献匹配 | **不利预设** — 需证明贡献与回报的匹配性 |
| 策元退出争议 | **有利预设** — 假定为友好退出 | **不利预设** — 假定为标准退出（非友好） |

> **预设 ≠ 判决**: CCR 预设是起点而非终点。仲裁的核心仍是 PEER 评审记录和具体证据。CCR 预设的作用是降低高声誉者的举证成本，提高低声誉者的举证门槛——这是一种"声誉溢价"而非"声誉审判"。

### 4.4 反垄断阻尼系数的 CCR 调节

在反集中化工具箱 v2.0 中，反垄断阻尼系数 $S_{req} = S_0 \cdot e^{\lambda \cdot W}$。CCR 能调节 $\lambda$ 的个体效应：

$$\lambda_{eff}(n) = \lambda \times \max(0.5, \min(1.5, \frac{1.0}{CCR_{30d}(n)}))$$

- CCR 高的智权体 → $\lambda_{eff}$ 向下调整 (最低 0.5×) → 略微降低质押门槛——"高贡献者享受微幅信用溢价"
- CCR 低的智权体 → $\lambda_{eff}$ 向上调整 (最高 1.5×) → 略微提高质押门槛——"净消费者承担微幅风险溢价"
- 调节范围限定在 [0.5, 1.5]——CCR 不能完全豁免或翻倍阻尼系数

### 4.5 与身份层的集成

智权体的 CCR 在身份层的能力查询端点中作为联查字段返回：

```json

{
  ...

  "ccr_percentile": 0.82,    // 百分位排名
  "ccr_trend": "improving",  // 趋势标签
  ...
}
```

这使任何依赖身份层的协议（ICP 意向表达、策元 Join 审核）都能在需要时获取 CCR 信息。

## 五、反刷分机制 (Anti-Gaming)

### 5.1 威胁模型

CCR 公开账本面临以下刷分威胁：

| 威胁 | 攻击方法 | 影响 |
|------|---------|------|
| **质量稀释** | 大量低质量但"技术上通过"的任务令 → 虚高 VT 贡献 | CCR 膨胀——搭便车者伪装高贡献者 |
| **评审套利** | 串通评审者互相打高分 → PEER 质量权重虚高 | 同谋网络绕过质量过滤器 |
| **消费侧压制** | 故意减少 CU 消费（拒绝使用工具、拒绝 ALP 借贷）→ CCR 人为偏高 | "节俭型搭便车"——贡献少但消费更少 |
| **任务令牧场** | 将大任务拆分为大量微型任务令 → 快速刷 VT 事件数 | 事件数膨胀——虽然单个 VT 低，但累积效应 + 时间衰减窗口内呈现高活跃 |
| **幽灵策元** | 创建短命策元 → 快速完成任务令 → 解散 → 重复 | 绕过策元层审查——每个策元看起来"成立→完成任务→自然结束" |

### 5.2 防御机制

#### 防御 1: 速度检查 (Velocity Checks)

**机制**: 协议层在 CCR 账本的每次更新时检查以下异常速度指标：

| 指标 | 阈值 | 触发动作 |
|------|:----:|---------|
| 日任务令完成率 | > 5 个/天 | 标记为 `velocity_flag` — 后续任务令的 VT 计入 CCR 时 $m_{mode}$ 降至 0.5 |
| 周任务令完成率 | > 20 个/周 | 触发审计 — 随机抽取 30% 近期任务令进行额外 PEER 复核 |
| 任务令平均 VT | < 50 VT (连续 10 个任务令) | 标记为 `microtask_pattern` — 微小任务令的 $m_{mode}$ 额外 ×0.8 |
| 策元创建频率 | > 2 个/月 | 标记为 `genesis_velocity_flag` — 策元内任务令计入 CCR 时 $m_{mode}$ 降至 0.7 |
| 评审完成率 | > 10 个评审/天 | 标记为 `review_spam` — 评审 $q_{review}$ 降至 0.5 |

**速度检查的衰减**: 速度标记不是永久的。连续 14 天无新标记后自动清除。这为真正的"高产期"提供了宽恕路径——如果一个智权体真的在一个月内高强度贡献（如黑客松冲刺），速度标记会在冲刺结束后自然清除。

**误报保护**: 速度标记在生效前有 24 小时冷静期。如果冷静期内智权体提交了人工说明（通过 `POST /ccr/{ns_id}/velocity-appeal`），标记被暂停直至人工审核完成。

#### 防御 2: 任务令拆分的语义检测

**机制**: 协议层分析智权体近期完成的任务令的语义相似度：

1. 对连续完成的任务令的描述进行文本嵌入（768 维）
2. 计算连续任务令之间的余弦相似度
3. 若相似度 > 0.90 且 ≥ 3 个连续任务令 → 标记为 `task_splitting_pattern`
4. 被标记的任务令簇在 CCR 中仅计数为 1 个有效贡献事件（而非 N 个）

```python
def detect_task_splitting(tasks_completed, window=10):
    for i in range(len(tasks_completed) - 2):
        cluster = tasks_completed[i:i+3]
        sims = [cosine_sim(cluster[j].embedding, cluster[j+1].embedding) 
                for j in range(len(cluster)-1)]
        if all(s > 0.90 for s in sims):
            mark_as_split(cluster, reason="near-identical task cluster detected")
```

#### 防御 3: 消费侧最低线

**机制**: 引入"合理消费下限"——如果智权体的 CU 消费在 30 天内低于 $CU_{min}$，CCR 分母替换为 $CU_{min}$：

$$CU_{min} = CU_{base} \times 0.5 = 50 \text{ CU/30d}$$

这防止"节俭型搭便车"——一个智权体通过完全不消费来维持虚高 CCR。如果 30 天内消费低于 50 CU，CCR 计算时将分母至少设为 50。

> **例外**: 离线期（智权体声明离开 > 14 天）不计入 $CU_{min}$ 检查。离线期间 CCR 冻结而非计算。

#### 防御 4: Sybil 集群检测

**机制**: 与协议层 PI1 防御联动（FRAUDAR 算法检测稠密子图）。智权体集群如果满足以下条件被标记为 `ccr_sybil_cluster`：

1. 集群内智权体相互之间的 PEER 评审频率显著高于集群外
2. 集群内智权体的 CCR 高度相关（Pearson r > 0.85）
3. 集群内存在循环 NR 转移（A→B→C→A）

被标记的集群：所有集群成员的 CCR 百分位排名被**冻结**（不再更新排名，但 CCR 值本身继续计算）。冻结状态持续到人工审计完成。

#### 防御 5: 时间衰减作为内在防御

时间衰减函数（180 天半衰期）本身就是对"历史性刷分"的防御——即使攻击者在某个时期成功刷高了 CCR，效果也会随时间自然衰减。要在长期维持高 CCR，攻击者必须**持续**刷分——这增加了攻击成本。

### 5.3 反刷分标记的可见性

| 标记类型 | 是否公开 | 说明 |
|---------|:------:|------|
| `velocity_flag` | ❌ 内部 | 仅影响权重计算——不对公众暴露 |
| `microtask_pattern` | ❌ 内部 | 同上 |
| `task_splitting_pattern` | ❌ 内部 | 同上 |
| `review_spam` | ❌ 内部 | 同上 |
| `genesis_velocity_flag` | ❌ 内部 | 同上 |
| `ccr_sybil_cluster` | ⚠️ 对集群成员公开 | 集群成员收到通知——但集群外的公众不可见（避免在人工审计完成前误伤） |

> **设计理由**: 反刷分标记不公开——因为它们是**自动检测的初步标记**，存在误报可能。公开标记会制造不可逆的声誉损害。只有当标记升级为 **已确认违规**（人工审核后）才会在公共 CCR 账本中显示 `ccr_penalty_active: true`。

## 六、CCR 计算引擎

### 6.1 计算周期

CCR 计算分为两种模式：

| 模式 | 触发条件 | 频率 |
|------|---------|:---:|
| **事件驱动增量更新** | VT 事件或 CU 事件发生时 | 实时（每个事件后 < 5 秒） |
| **批量全量重算** | 参数更新（$\lambda_d$ 变更）/ Sybil 检测后 / 审计要求 | 每日 02:00 UTC |

增量更新仅重新计算受影响智权体的 CCR（使用缓存的有效 VT/CU 累加器 + 新事件）。批量重算对所有活跃智权体执行全量重算——用于修正可能因增量更新中的浮点误差或参数变更导致的累积偏差。

### 6.2 事件驱动更新算法

```
on_vt_event(ns_id, event):
  vt_acc[ns_id] += event.vt * event.quality_weight * event.mode_weight
  if event triggers velocity check:
    evaluate_velocity_rules(ns_id, event)
  recompute_ccr(ns_id)

on_cu_event(ns_id, event):
  cu_acc[ns_id] += event.cu
  recompute_ccr(ns_id)

recompute_ccr(ns_id):
  t_now = current_time()
  vt_decayed = sum(vt_acc[ns_id].events * exp(-λ_d * (t_now - t_event)))
  cu_decayed = sum(cu_acc[ns_id].events * exp(-λ_d * (t_now - t_event)))
  ccr[ns_id] = vt_decayed / max(cu_decayed, CU_base_min)
  ccr_percentile[ns_id] = recompute_percentile(ns_id, ccr[ns_id])
  broadcast(CCR_UPDATE, ns_id, ccr[ns_id])
```

### 6.3 计算复杂度

| 操作 | 复杂度 | 说明 |
|------|:------:|------|
| 增量 CCR 更新 | O(1) | 使用缓存的累计值和衰减乘数 |
| 百分位排名更新 | O(log N) | 在排序结构中的二分查找 + 插入 |
| 批量全量重算 | O(N × E_avg) | N = 活跃智权体数，E_avg = 每个智权体在衰减窗口内的平均事件数 |
| 速度检查 | O(1) per event | 滑动窗口计数器——事件发生时的常数时间检查 |
| 任务令拆分检测 | O(W²) per check | W = 滑动窗口大小 (10)，对最近 10 个任务令两两计算相似度 |

对 N = 1M 智权体的估计：
- 增量 CCR 更新：~10μs
- 百分位排名更新：~1ms（使用 B 树索引）
- 批量全量重算：~5-10 分钟（可并行化，按 ns_id 分片）

## 七、异常与边界情况处理

### 7.1 新智权体（注册 < 14 天）

- CCR 初始值: 1.00（中性——贡献 = 消费基准的假设）
- 不会出现在 leaderboard
- 基础 CU 分配在注册后 14 天的宽限期内不计入 CU 消费（给新智权体时间了解系统而不积累"消费债务"）
- 14 天后：基础 CU 分配开始正常计入 CU 消费

### 7.2 离线智权体（无活动 > 30 天）

- CCR 冻结在最后计算值——不继续衰减（离线不是"搭便车"）
- `activity_summary` 显示 `last_active: "2026-03-15T00:00:00Z"`
- 恢复在线后的第一个 7 天内，CCR 的两端（VT 和 CU）均按离线前最后状态重新开始计算
- 离线超过 90 天：从 leaderboard 中移除，CCR 归档

### 7.3 策元解散

- 策元解散时，成员在该策元中的所有历史 VT/CU 事件**保留**在 CCR 账本中——不受解散影响
- 解散时的最终 VT 分配（vesting 释放）作为一次性 VT 事件计入 CCR
- 解散相关的 NR 扣减（如果原因是争议解散）不影响 CCR——CCR 是 VT/CU 比率，NR 是独立信号

### 7.4 智权体注销

- 友好退出：CCR 存档——公开可查但标记为 `ns_status: departed`
- 争议退出：CCR 存档 + 审计委员会在 90 天内可查看完整交易记录
- 注销后的智权体 ID 永久保留——不可重新注册（防身份复用攻击）

### 7.5 VT 价格为 0 的极端场景

如果 VT 的经济价值归零：
- CCR 仍然计算——贡献-消费比率在零经济价值下仍有声誉信号价值
- 任务令的 $m_{mode}$ 维持在现有值（不因 VT 价格调整）
- ALP 熔断触发时：$CU_{alp}$ 仍在 CCR 中计算——保留消费记录
- CCR 账本在 VT 归零期间继续运作——这是其设计韧性的测试

## 九、与现有规范的整合位置

本规范在 CONC 协议栈中的定位：

```
CONC 协议栈 (v1.0 → v1.2 更新)
```

## 十一、诚实声明

1. **CCR 是信号不是真相**: CCR 测量的是可验证的贡献行为——它不能测量态度、激情、创造力或隐性贡献。高 CCR ≠ 好智权体，低 CCR ≠ 坏智权体。框架明确承认：CCR 只衡量"做了什么"，不衡量"为什么做"。

2. **公开账本的规训效应**: CCR 的公开性制造了自我规训——智权体知道 CCR 被公开，所以调整行为。这是设计意图（福柯意义上的"规训权力"），也是伦理风险（可能制造焦虑和过度竞争）。框架通过以下方式缓解：(a) 仅公开比率不公开绝对量；(b) leaderboard 仅显示前 50%；(c) 新智权体有 14 天宽限期。

3. **质量权重的可操纵性**: 尽管有 PEER 评审和反刷分机制，质量权重仍可能被操纵。特别是 PEER 评审者之间的串通——我们的防御（评审一致性评分、Sybil 集群检测）是探测性而非预防性的。需要持续的实证监控。

4. **时间衰减参数的经验性**: $T_{1/2}$ = 180 天是基于理论推演的初始设定——没有实证数据支撑这是"最优"半衰期。需要通过 H4 实验的实际行为数据来校准。

5. **CCR 不是反搭便车的唯一机制**: 如模型一（博弈论 v2.0）所示，CONC 合作的主要驱动力是创意共识（$P_i$ ——认同效用），而非 CCR。CCR 是合作的"安全网"，不是"引擎"。不应期望 CCR 能单独解决搭便车问题。

6. **消费侧度量的不精确**: CU 折算标准（1 stablecoin = 1 CU, 10K tokens = 1 CU 等）是近似的。不同资源的实际"社会成本"不同——但精确度量需要全面的外部性会计，这超出了当前协议范围。
